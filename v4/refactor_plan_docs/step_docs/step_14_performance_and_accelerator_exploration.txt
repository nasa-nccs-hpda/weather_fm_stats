Step 14: Improve v4 Performance And Optional Accelerator Usage

Status
- In progress.

Reason For This Step
- Step 12 timing tests showed v4 is structurally cleaner and more stable, but
  it is not yet faster than the original v1 multi-job workflow.
- v1 can win wall-clock time by fanning work out across many SLURM jobs, while
  v4 currently limits execution to one allocation and local worker processes.
- Compute is acceptable to spend when it produces a meaningful speedup, but
  stability and output equivalence should remain the default priority.

Primary Goals
- Identify the main v4 runtime bottlenecks by phase and branch.
- Improve CPU utilization without returning to the full v1 dependency-chain
  model.
- Add performance controls that are explicit in YAML and safe by default.
- Explore optional GPU acceleration only for measured hotspots with a CPU
  fallback.
- Preserve scientific output equivalence with v1/v4 Step 12 validation outputs.

Planned Work
- Profile source dataset creation, merge, regional statistics, and global
  statistics using existing timing/resource summaries and additional targeted
  measurements if needed.
- Compare v1 global-stat SLURM fan-out against v4 in-process worker fan-out.
  A v1 long-run global chunk processed 2 init dates in about 3:47 using 1 CPU
  at about 94% CPU utilization and 3.45 GB max RSS. Because v1 can launch 16
  global chunks as separate SLURM jobs, it may be using far more concurrent
  global-stat workers than v4's current single-allocation worker settings.
- Add separate regional/global statistics chunk-size controls if testing shows
  they need different chunk sizes.
- Test higher worker counts for forecast, analysis, regional stats, and global
  stats where memory allows.
- Initial global-stat experiment: test v4 with higher global concurrency while
  keeping the same memory request, using pipeline_cpus=16, pipeline_mem=64G,
  pipeline_max_workers_stats_global=16, and
  pipeline_chunk_size_stats_global=2, then compare global wall time, max RSS,
  and output equivalence against the Step 12 baseline.
- Keep climatology tuning conservative because previous tests showed memory and
  stability sensitivity.
- Explore optional regional/global branch concurrency behind a YAML setting,
  while keeping serial execution as the default.
- Investigate process startup and repeated dataset/config loading overhead in
  chunk workers.
- Investigate data loading, NetCDF/HDF5 I/O, and merge bottlenecks before
  assuming more CPU workers will help.
- Consider a coarse multi-allocation mode only if single-job tuning remains
  slower and the added SLURM orchestration is justified.
- Evaluate GPU acceleration candidates only after profiling identifies a
  GPU-friendly hotspot.

Out Of Scope For This Step
- Do not change scientific formulas.
- Do not make GPU acceleration mandatory.
- Do not remove the stable CPU execution path.
- Do not reintroduce the full v1 many-job dependency-chain design.
- Do not make regional/global branch concurrency the default until filesystem
  and memory behavior are validated.

Potential YAML Controls
- pipeline_chunk_size_stats_regional
- pipeline_chunk_size_stats_global
- pipeline_stats_branch_execution: serial | parallel
- pipeline_max_concurrent_stats_branches
- pipeline_accelerator: cpu | gpu
- pipeline_gpu_stats: true | false
- pipeline_gpu_regrid: true | false

Planned Acceptance Criteria
- Step 14 identifies at least one measured v4 bottleneck and records the
  evidence.
- Any new performance controls are optional, YAML-driven, and documented.
- Default behavior remains stable and CPU-only.
- Output files remain scientifically equivalent to the Step 12 validation
  baseline.
- Performance changes are validated on the short and long example YAMLs.

Validation Notes
- Latest v1 observation: one global statistics chunk used 1 CPU efficiently
  and finished in 3:47 for 2 init dates with 3.45 GB max RSS. The likely v1
  wall-time advantage is coarse SLURM-level concurrency across many chunks, not
  faster per-chunk computation. Step 14 should test whether v4 can recover that
  speed by increasing in-process global-stat workers inside a larger single
  allocation before considering a coarse multi-allocation mode.
- First implementation pass added branch-specific statistics chunk-size
  controls while preserving pipeline_chunk_size_stats as the fallback. The
  example YAMLs now request 16 CPUs and 64G memory, keep regional stats at 8
  workers with 4-date chunks, and test global stats at 16 workers with 2-date
  chunks. Dataset and climatology settings were left conservative.

Known Risks
- Higher worker counts can increase memory pressure, especially for
  climatology and global statistics.
- Regional/global branch concurrency can increase shared-read pressure on the
  same fcst/ana/clim datasets.
- GPU acceleration may not help if the dominant bottleneck is I/O, process
  startup, xarray overhead, or sparse regridding behavior.
