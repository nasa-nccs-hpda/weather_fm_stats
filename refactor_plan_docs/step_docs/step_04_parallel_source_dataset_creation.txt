Retrospective Gap
- Step 4 was named as general source dataset parallelization, but the actual implementation focused on forecast init-date chunks.
- Analysis and climatology dataset processing still run in the follow-up process_batch(...) call after forecast merge.
- Regridding inside that follow-up path remains sequential across analysis valid times and climatology cycles.
- This became visible during larger-YAML testing after Step 6, where ana/clim regridding remained a bottleneck.
- A new refactor step should extend deterministic chunk planning and plan-aware merge validation to ana and clim datasets.

Known Limits
- Forecast is the only source dataset currently parallelized.
- Ana and clim are still processed as follow-up work after forecast processing, including their regridding.
- Collection-level parallelism was planned but does not appear to be implemented.
- The executor still uses implicit state changes such as setting model names to empty strings to disable dataset types.
- Chunk result order is based on completion order when ProcessPoolExecutor uses as_completed(...), so future deterministic chunk planning should not rely on that list order.
- Forecast chunk merge currently discovers files from the tmp directory and sorts filenames; future work should make expected chunk identity explicit before merge and cleanup.
- Merged output validation before deleting chunk files is still limited.

Notes For Future Steps
- The next refactor should make chunk planning deterministic and reusable before adding statistics chunking.
- A shared chunk plan should cover chunk index, start/end indices, selected init dates, expected output path, and expected completion state.
- Statistics chunking should not duplicate the forecast-specific chunk assumptions currently embedded in dataset_parallel_executor.py.
